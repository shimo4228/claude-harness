## Summary

`llm-as-judge` の判定定義（二値チェックの問いと verdict enum の境界文）を仮説として扱い、固定した下流評価で候補を比べる外側ループを足す提案。

## Motivation

`llm-as-judge` は judge の**中身**を設計する skill で、問いの集合と verdict の定義は著者が手で決めて固定する。「修正後は同じ問いで 1 回だけ再判定」は、判定のたびに基準が動くことを防ぐ。しかし、**問いの集合と verdict の境界そのものが正しいか**を確かめる仕組みは無い。

HELLO_CYBERNETICS「JevとDSPyで『何を分類するか』まで最適化できるか」（Zenn, 2026-09-27）がこの穴を言語化している。要点は 3 つ。

1. 業務目標を分類問題へ翻訳する時点で、学習とは別の仮説が入る。分類を完璧にしても、同じラベルに必要な行動が 2 つあれば後段は区別できない
2. Jev はクラスの意味（選択肢の説明文）を推論時の入力として受け取るので、定義を差し替えて試せる
3. 中間ラベルの正答率ではなく、下流の行動で採点する評価を固定すれば、分類体系の案同士を比べられる

この harness の側にも、定義の問題を示す実測が既にある。

- [RFC-0024](0024-typesafe-jev-as-offload-for-max-quota.md) の検証で、**Choice の confidence は 0.4〜0.7 で頭打ち**、Noul は 0.72〜0.82 で安定した。英訳で逆に下がったので、頭打ちの原因は言語ではなく判定自体の曖昧さとされた。これはモデルの精度ではなく**問いの切り方**の問題で、記事のいう「分類問題の設計」に当たる
- `llm-as-judge` は既に「verdict enum の各値を次の行動に 1:1 で対応させる」を原則に持つ。記事が外側評価の前提として求める**行動の層**を、この skill は最初から持っている。欠けているのは、その層を固定したまま定義の案を比べる手順だけ

## Guide-level explanation

ループを 2 つに分ける。

- **内側（既存）**: judge は固定された問いと verdict 定義で判定する。出力に点数は無い
- **外側（新設・オフライン・低頻度）**: 定義の候補を作り、各候補で judge を走らせ、下流の行動の当たり外れで候補を比べる

skill の 3 原則との対応:

| skill の原則 | 記事の概念 | 外側ループでの扱い |
|---|---|---|
| ① 二値チェック | Noul / 中間判定 | 問いの文面・分け方が探索変数になる |
| ② named verdict（行動と 1:1） | Choice の `(id, 説明文)` と行動ルール | 説明文（境界）と閾値が探索変数。id と行動の対応は固定 |
| ③ 集計しない | — | **judge の出力は引き続き採点しない**。外側で点数が付くのは judge の**設計**であって、判定対象の品質ではない |

③ との区別がこの提案の要点。外側の数値は「この定義で判定すると、行動をどれだけ取り違えるか」を測る。成果物の品質スコアとして使わず、judge にも見せない。

新しい規律を 1 つ足す: **問題設定を動かすほど、評価は固定する**。外側の評価関数・正解行動のラベル・重みは探索を始める前に凍結し、候補生成の側から触れない。判定しやすい範囲へ定義を狭めて見かけの一致率を上げる逃げ道を塞ぐため。skill の「同じ問いで再判定」と同じ向きの規律を、一段外側に置く形になる。

診断にも使える。中間の二値チェックを人手の正解に差し替えても verdict が外れるなら、問いの精度でなく verdict の切り方か行動ルールが悪い。差し替えで当たるなら、問いの文面を重点的に直す。

## Reference-level explanation

### 何を動かすか（記事の表を harness に写したもの）

| 動かすもの | 手段 | 前提 |
|---|---|---|
| Noul の閾値、Choice の選択肢重み | DSPy の ReAnchor（記事時点で 3.4.0、experimental） | Jev 判定器に限る。RFC-0025 の registry が較正データ |
| verdict の説明文、二値チェックの文面 | 外側で候補を生成し、`set_criteria()` 等で差し替えて評価 | No の列挙を失敗例として反省させる GEPA 型の候補生成が使える |
| enum の数、Choice → 複数 Noul への分解、行動ルール | Signature と後段の再構成（手組み） | RFC-0024 の Choice 頭打ちへの本命の打ち手 |

記事によれば DSPy 3.4.0 の時点で、TypeSafe 判定器を生成系 Optimizer で扱うのは未対応。したがって 2 段目と 3 段目の外側ループは自前で書く。ReAnchor が書き換えるのは数値だけで、説明文や分類体系は書き換えない。

### 外側評価

- 単位は「verdict から dispatch された行動」と「本来取るべきだった行動」の一致
- 取り違えは重み付きで数える。重大な見落とし（dominant No を通した）と過剰な差し戻しの重みは**探索前に著者が決める**。skill の「dominant No は単独で決める」を外側の重みとして表現したもの
- データは 3 分割する: 閾値合わせ用 / 候補選択用 / 最終確認用。最終確認用は探索に一切使わない
- 定義を変えた行は RFC-0025 の暫定回答どおり、`question_hash` が違う別分布として読む

### skill 本体への反映

`llm-as-judge` SKILL.md に 1 節（「判定定義を仮説として扱う」）を足すのは**原則だけ**: 外側は設計を採点し成果物を採点しない / 動かすほど評価を固定する / 中間判定の人手差し替えで原因を切り分ける。DSPy 等の実装は skill に入れない。skill はモデル非依存のまま保つ。

### パイロット候補

外側評価には「本来取るべき行動」が観測できる judge が要る。

- **jev-skill-router**: shadow の判定ログが RFC-0025 経由で既に溜まっている。skill の実使用ログと突合できる
- **skill-stocktake の verdict**: 行動（Keep / Improve / Retire …）が明示的で、決定論の事前検査（存在確認）がラベルの一部を自動で埋める

## Drawbacks

- **③ と緊張する**。外側とはいえ数値を導入するので、いずれ judge 側へ漏れて「点数で合否」に戻る危険がある。層の分離を skill の文面で明示する以外に防ぎようがない
- **反実仮想が観測できない**。ログに残るのは実際に取った行動の結果だけで、ルーターが skill を読まなかった回に「読むべきだったか」は見えない（記事の Off-Policy Evaluation の指摘と同じ）
- **n が小さい**。harness の judge は高頻度のものが少なく、候補を多数比べると選択用データに過適合する
- **枠を食う**。候補生成は上位モデルの仕事で、RFC-0024 が問題にした Fable 枠を再び消費する
- **外部依存が増える**。DSPy の experimental API に乗る部分は壊れやすい

## Rationale and alternatives

- **何もしない** — N=1 の単発ゲート（`learn-eval` / `skill-creator` §4）では妥当。定義を比べるほど判定回数が無い
- **ReAnchor の閾値較正だけ行う** — 安く済むが定義に触れない。RFC-0024 の実測は、問題が閾値でなく切り方にあることを示している
- **PydanticAI + pydantic_evals** — 型付き出力と評価はあるが、評価結果から定義を探索する仕組みが無い。この提案の外側ループを手で書くのと同じになる
- **専用分類器を学習する** — 定義を変えるたびに再ラベル・再学習が要る。Jev を入れた理由（定義を推論時入力にできる）を捨てることになる

## Unresolved questions

- **「本来取るべき行動」のラベルを誰が付けるか**。LLM に付けさせると、その採点者の基準も凍結対象になり、再帰する
- **どこまで溜まれば候補比較を始められるか**。RFC-0025 と同じく、必要な観測数の見積もり方がまだ無い
- **置き場**: `llm-as-judge` への 1 節で足りるか、定義探索を別 skill に切り出すか
- **Jev 以外の judge（Claude subagent）にも外側ループを当てるか**。原理はモデル非依存だが、ReAnchor の段は使えず、1 回の評価が重い

## Future possibilities
