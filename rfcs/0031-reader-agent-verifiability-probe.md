## Summary

公開物だけを読める外部の読者役エージェントに、決まった対象の「出力 → 指摘 → 理由 → 結果」を辿らせ、各環を URL つきで `確認` / `記述のみ` / `不明` に判定させる。公開の仕方を変えるたびに同じ対象で走らせ、`確認` の環が増えたかを数える。RFC-0027（指摘と Eval を公開物だけで照合できるようにする）が効いたかを測る計器。

## Motivation

RFC-0027 は「あなたの判断は公開物で辿れる」と言えるようにする方針で、RFC-0028（commit に指摘を残す）・RFC-0029（commit 本文を公開ミラーへ運ぶ）・RFC-0030（Eval カード）がその手段。手段が効いたかは、書いた側の自己申告では分からない。文脈を持たない読者が公開 Web だけで辿れたかを、環ごとの事実（その URL で辿れた / 辿れなかった）として数える。点数を付けないので、著者の好みを採点する Eval にはならない。

**予備測定（2026-09-27、RFC-0027 の調査の中）**: 公開済みの 5 件・20 環で、`確認` 3（すべて「結果」の環）・`記述のみ` 13・`不明` 4（記事 1 件の全環）。対照は、辿れるはずの existence-proof が 4/4 `確認`、辿れないはずの AKC ADR-0024 が 0/4 で、判定は期待どおり分かれた。辿れなかった理由は読解ではなく証拠の置き場所だった — 根拠が private repo の commit 本文、gitignore 下のログと下書き、会話にしか無い。5 件のうち記録に残るのは RFC-0021（4 環とも `記述のみ`、根拠の commit 本文が private repo にしか無い）だけで、残りの対象の一覧と各環の判定は失われた（同日の session ログも見つからない）。1 回目との比較はできないので、下の固定リストで基準を取り直す。

## Guide-level explanation

1 つの対象について、読者役は 4 つの環を辿る。

| 環 | 中身 | 例（ADR の場合） |
|---|---|---|
| 出力 | エージェントが作ったもの | ADR の本文 |
| 指摘 | それに対する著者の修正・判断 | 著者が方針を変えた発言、却下 |
| 理由 | なぜそう直したか | commit 本文の Context / Decision、plan |
| 結果 | 直した後どうなったか | 後日の注記、Review-when の発火、測定 |

判定は 3 語: `確認`（公開物の中で根拠まで辿れた — URL を示す）/ `記述のみ`（「こうした」と書いてあるが根拠が公開されていない）/ `不明`（見つからない）。

## Reference-level explanation

**対象（固定、4 件 + 1 枠）** — 公開の仕方を変えた手段が、それぞれどの環に効くはずかで選んだ。

1. RFC-0021（claude-harness `rfcs/0021-verify-full-red-growth-fable-ty.md`）— 予備測定で唯一記録の残る対象。RFC-0029 が実装されれば「理由」の環が動くはず
2. ADR-0085 と plan `docs/plans/composed-enchanting-wand.md` — plan が「読者役を当てると出力と Expect の環が `確認` になる」と事前に予測している（外れうる予測）
3. Eval カード s1（`docs/evals/s1-headline-craft-native-ablation-2026-09-13.md`）と skill-creator §5 — RFC-0030 の「結果」の環
4. RFC-0035 と task-triage の packet 規約 — plan（packet）→ commit の `Plan:` 行の鎖
5. **枠: 走らせた時点で最新の zenn 記事** — RFC-0028 の試行（2026-09-28〜10-12）が効けば「指摘」の環が動くはず。記事は回ごとに替わるので、固定するのは「最新の 1 本」という選び方

**対照（固定、2 件）**: existence-proof（https://github.com/shimo4228/existence-proof、辿れるはず）/ AKC ADR-0024（agent-knowledge-cycle `docs/adr/0024-judge-build-human-three-role-loop.md`、辿れないはず）。対照の判定が期待と逆に出たら、その回は計器の故障として読まない。

**読者役**: fresh context の subagent。道具は WebSearch / WebFetch だけ（repo の手元コピーを読ませない）。model ID を結果に記録し、回をまたいで同じ model を使う（替えたら別系列として数える）。

**いつ走らせるか**: 定期ではなく、公開の仕方を変える手段が 1 つ入るたび（儀式化を避ける）。予定: 基準の 0 回目（採用時）、RFC-0028 の試行の読み（2026-10-12）の後、RFC-0029 を実装したら。

**結果の置き場所**: 1 回を Eval カード 1 枚にする（`docs/evals/`、RFC-0030 の形式）。環ごとの判定と URL を「生の読み値」に、読者役の model と道具を「環境」に、対照の判定を「有効性の状態」の根拠に書く。

## Drawbacks

- 読者役の誤判定と、WebFetch の要約器を経由した引用のずれ。対照 2 件で故障は検出できるが、個々の誤判定は残る
- 回を重ねると、測ること自体が目的になりうる — 走らせるのを手段の導入時だけにし、review-when で止める
- 1 回ごとに Web の取得が 20 回前後かかる

## Rationale and alternatives

- **script で機械的に検査する**（commit 本文が公開 repo にあるか、リンクが開けるか）: 安くて決定的だが、「文脈を持たない読者が実際に辿れるか」は測れない。リンクの死活は既存の context_evidence のゲートが持つ
- **やらない**: 手段（0028〜0030）が効いたかを自己申告でしか言えなくなる
- **予備測定の対象を復元する**: 一覧が失われていて復元できない

## Unresolved questions

- 読者役に使う model（判断役と同じ系統か、別系統か）
- 枠 5 の記事を「最新」でなく、RFC-0028 の試行で書いた記事に固定するか
