# README Judge Checklist（readme-judge が読む基準の正本）

`readme-judge` agent は判定の前にこのファイルを全文読む。フロア 5 要素・Voice 規約の骨格は
`../SKILL.md` にあり、判定の問いはここにだけ置く。

判定の型（正本は `~/.claude/skills/llm-as-judge/SKILL.md`）: 二値チェックに 1 行の引用証拠 →
反証 → **集計しない** named verdict（Publishable / Fix / Rewrite）。

## §E 証拠層（`scripts/readme_evidence.py` の JSON。判定はしない）

判定器は JSON を**証拠として**読み、件数で verdict を決めない。JSON の `notes` が各カウンタの
盲点を書いている（例: 造語候補は backtick / bold だけで、地の文の造語は判定器が拾う）。

| key | 判定器がそこから問うこと |
|---|---|
| `first_screen` | 最初の H2 までに何行・何語の新語・何本の内部参照が来るか（R1–R3 / R10） |
| `insider_refs` / `own_repo` | ADR 番号・他 repo・docs/ への参照 — 参照を消して文が立つか（R11）。自分の repo は数えない |
| `term_candidates` | backtick / bold の語の出現表 — どれが造語で、gloss があるか（R10） |
| `details_blocks` | 折りたたみの中身 — フロアや AI 向け導線が隠れていないか（F3） |
| `figures` | 図の前後 2 行に prose があるか（`prose_adjacent`）と alt（F2 / R15） |
| `structure` | 見出しの飛び・切れたローカル参照・切れた `#anchor`（`broken_anchors`）・alt の無い画像 |
| `history_signals` / `numeric_claims` | 内部史・生数値の行（R12 / R13） |
| `prose_signals` | slop 語・em-dash・予告列挙・呼びかけ（R8） |
| `register_ja` | 日本語版の地の文の文末（ですます / 常体）と常体の行（J1） |

## §F フロア（非交渉の最小コア。有無を問う）

| # | 質問 |
|---|---|
| F1 | フロア 5 要素（`../SKILL.md`）が本文の文として在るか — 画像だけ・`<details>` の中だけ・リンク先だけは数えない。研究 / DOI repo は DOI と引用方法（BibTeX / CITATION）があるか |
| F2 | どの図にも、前後の本文にテキスト等価（図の中身を言う文）と alt があるか |
| F3 | フロア以外の情報が `<details>` や図やフロア節に溜め込まれていないか（偽装 llms-full.txt） |

## §R 固定コア

### R-A 第一画面（訪問者は最初の 1 画面で「自分向けか」を決める）

| # | 質問 |
|---|---|
| R1 | identity 文（H1 直後の 1–2 文）が「何を / 誰向けに / どこで動くか」を、**読者がまだ知らない語を使わずに**言っているか。第一画面だけ読んで何者かを 1 文で言えるか |
| R2 | tagline（あれば）が価値提案を 1 行で運んでいるか — 題名の言い換えや抽象形容詞になっていないか |
| R3 | identity と canonical な事実（名前・stack・必要な鍵・DOI）が deep rationale より前に来ているか |
| R15 | 概要図（あれば）: 図のラベルが本文の語と一致し、図に出る固有名が tagline か図の直後の段落で説明され、各枠の内容が直後の段落と alt で文として言われているか |

### R-B 文の密度

| # | 質問 |
|---|---|
| R4 | 単数の読者に向けて書かれているか（「皆さん」型の呼びかけ・企業 IR 調の主語なし文がないか） |
| R5 | 能動態が主か（受動態の連鎖で主体が消えていないか） |
| R6 | 抽象形容詞（powerful / robust / 画期的）でなく具体像で語っているか |
| R7 | 各段落・各 bullet について「読者のどの問いに答えるか」が 1 行で言えるか。言えない段落は削除候補として名指す |
| R8 | 企業メモ調・AI slop（診断表の正本は writing-ecosystem — zenn-content 常駐）・em-dash 連打・予告つき triad になっていないか |
| R9 | 主張を言い切っているか（ヘッジの積み重ねで何も言っていない文がないか） |

### R-C 文脈予算（継ぎ足しで育った README の病因）

| # | 質問 |
|---|---|
| R10 | **造語**: repo 固有の造語を出現数付きで棚卸しし（地の文の造語も判定器が拾う）、README 全体で残す語が **~6 個**以内、第一画面の新しい造語が **2 個**以内か。残す語は初出に一行の平易な言い換えがあるか。それ以外は平易な言い換えか docs/ への移動になっているか。1 文に造語 2 個以上を強いていないか |
| R11 | ADR 番号・他 repo・evidence ファイルへの参照は**導線であって説明の代替ではない** — その参照を消しても文が意味を運ぶか |
| R12 | 内部史（version 番号・モデル交代・「7 → 2」型の変遷・「以前は」）は、読者の問いに答えるときだけ残っているか |
| R13 | 数値は README 内で読者が解釈できるときだけ置かれているか（比べる相手・単位・範囲が近くにあるか） |
| R14 | Quick Start の前提（外部サービス登録・ハード要件・必要な鍵の種類と有料か）が README 内で説明されているか |

## §J 日本語版と言語間の対応

| # | 質問 |
|---|---|
| J1 | 日本語版の地の文がですます調か（`register_ja` を証拠に。表のセル・体言止め・見出し・alt は対象外） |
| J2 | 漢語直写・翻訳調（`ja-register.md` の対応表）・日本語で言える語の英語のままの埋め込みが無いか。日本語の文の途中で改行していないか（GitHub では空白に見える） |
| J3 | 英語版の自称（I / we / the author）が 1 つの README の中で揃い、identity 文が三人称の型か |
| J4 | 言語版どうしで、フロア・見出しの階層・アンカー・例・概要図の枠・事実の強さ（頻度・数値）が揃っているか。英語だけの docs へのリンクが日本語版で（英語）と分かるか |

## §K 著者の実指摘から一般化した 6 問

| # | 質問 |
|---|---|
| K1 | **as-of 整合**: 「現在〜で動いている」「最新は〜」型の主張が、README に書かれた時点情報（version・日付）と釣り合っているか。外の世界についての主張に as-of か出典があるか |
| K2 | **継ぎ足し検出（節単位が主）**: 足された bullet が、重複・矛盾・同型反復になっていないか。各節の小結論を順に並べたとき一本の線を成すか。README は commit 数に比例して継ぎ足されるので、この項を主力にする |
| K3 | **主張の論理**: 場合分け・排他・数量を主張する文（「〜しかない」「必ず」「2 依存だけ」型）を全て抜き出し、各々に反例を 1 つ探してから Yes を出す。反例を潰す論が本文になければ No — 本文にない防御を判定器が自作して通さない |
| K4 | **指示語・先行文脈依存の回収**: 前の節を読んでいないと回収できない参照を、初見読者が近傍で回収できるか |
| K5 | **目的の欠落**: 詳細に入る前に、読者が「この repo は何のためにあるか」を言えるか。what / how / who に答えて why だけ欠けていないか。見出しの有無で判定しない。道具でない repo（実験・観察装置）が「〜向けのツール」型の対象者文を持っていないか |
| K6 | **lead の約束の行き先**: lead が産物・実績・結論を約束するとき、README から到達できる行き先（リンク・節・as-of 付きの数）があるか |

## §C 主張の照合（Phase B。README だけの判定を凍結した後）

README の検査できる主張（version・コマンド・flag・設定キー・既定値・path・ファイル名・件数・上限・
「only / never / always / all」・as-of 日付）を repo のコード・設定・docs と照らし、`file:line` を
添える。llms.txt・llms-full.txt・graph.jsonld があれば、README と食い違う箇所も挙げ、どちらが古いかを
添える（llms.txt 側を直すのは llms-txt-writer）。README 側の食い違いは Fix の項目にする。repo で決着しない外の世界の主張は `external` とし、K1 だけで
扱う。Phase B は Phase A の答えを変えない。

## §A アンカー比較（張り付き回避）

必ず答える: 「このチェックリストを完全に体現した README と比べて、本稿が**劣る点はどこか**」
— 最低 1 点、最大 3 点。Publishable を出す場合でも埋める。**著者自身の他 repo README を
アンカーに使わない**（同じ癖を基準に持ち込む）。

## §D ループ設計への制約

- 改稿ループは上限 2 ラウンド。2 ラウンド目以降は voice の正規化ドリフト（企業 About 化）が始まる。
  Fix は span 単位の指摘のみで、全文書き直し案を出さない
- 章立てテンプレを「埋める」加筆を Fix に出さない: 節が足りないことは欠陥ではない。読者の問いに
  答えない節があることが欠陥
- 評価は欠陥検出に限定し、文体の方向づけに使わない（judge の好みへの収束 = 平坦化を起こさない）
- 反証で覆らなかった No が 1 つでも残れば Publishable にしない。反証で覆った No は Yes に戻す

## 判定注意

- §E の件数だけで verdict を決めない（ADR 参照 28 箇所は証拠であって判定ではない — 全部が導線として
  機能していれば Publishable でありうる）
- dominant question: **「初見の読者の時間を尊重しているか」**（density over completeness）。
  網羅性は docs/ と llms-full.txt の仕事
