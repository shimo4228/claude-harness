# README Judge Checklist（readme-judge が読む基準の正本）

`readme-judge` agent は判定の前にこのファイルを全文読む。zenn-content の
`kaguura-craft-checklist.md` と同じ役割 — 判定器の固定コア質問を SKILL.md 本文から分離し、
改定履歴をここに集める。フロア 5 要素・Voice 規約・造語規約の正本は
`../SKILL.md` にあり、ここでは**参照**するだけで複製しない。

判定の型（正本は `~/.claude/skills/llm-as-judge/SKILL.md`）: 二値チェックに 1 行の引用証拠 →
反証プレッシャーテスト → **集計しない** named verdict（Publishable / Fix / Rewrite）。

## §E 証拠層（`scripts/readme_evidence.py` の JSON。判定はしない）

判定器は JSON を**証拠として**読む。件数で verdict を決めない。使い方の目安:

| key | 判定器がそこから問うこと |
|---|---|
| `first_screen` | 最初の H2 までに何行・何語の新語・何本の内部参照が来るか（R1–R3 / R10） |
| `insider_refs` | ADR 番号・他 repo・docs/ への参照が何箇所か — 参照を消して文が立つか（R11） |
| `term_candidates` | backtick / bold の語の出現表 — どれが造語で、gloss があるか（R10） |
| `details_blocks` | 折りたたみの中に何が入っているか — フロアや AI 向け導線が隠れていないか |
| `figures` | 図の直後に prose があるか（テキスト等価） |
| `history_signals` / `numeric_claims` | 内部史・生数値の行（R12 / R13） |
| `prose_signals` | slop 語・em-dash・予告列挙・呼びかけ（R8） |

## §R 固定コア（README 固有。判定器の独自領域は R-A / R-B / R-C）

### R-A 第一画面（訪問者は最初の 1 画面で「自分向けか」を決める）

| # | 質問 |
|---|---|
| R1 | identity 文（H1 直後の 1–2 文）が「何を / 誰向けに / どこで動くか」を、**読者がまだ知らない語を使わずに**言っているか |
| R2 | tagline（あれば）が価値提案を 1 行で運んでいるか — 題名の言い換えや抽象形容詞になっていないか |
| R3 | identity と canonical な事実（名前・stack・DOI）が deep rationale より前に来ているか |

### R-B 文の密度（記事の B6–B9 / B14–B15 の README 版）

| # | 質問 |
|---|---|
| R4 | 単数の読者に向けて書かれているか（「皆さん」型の呼びかけ・企業 IR 調の主語なし文がないか） |
| R5 | 能動態が主か（受動態の連鎖で主体が消えていないか） |
| R6 | 抽象形容詞（powerful / robust / 画期的）でなく具体像で語っているか |
| R7 | 各段落・各 bullet について「読者のどの問いに答えるか」が 1 行で言えるか。言えない段落は削除候補として名指す |
| R8 | 企業メモ調・AI slop（正本は writing-ecosystem — zenn-content 常駐）・em-dash 連打・予告つき triad になっていないか |
| R9 | 主張を言い切っているか（ヘッジの積み重ねで何も言っていない文がないか） |

### R-C 文脈予算（継ぎ足しで育った README の病因。この節が README 版の独自コア）

| # | 質問 |
|---|---|
| R10 | **造語予算**: repo 固有の造語を出現数付きで棚卸しし、README 全体で **~6 個**に収まっているか。各造語の初出に一行の平易な言い換えがあるか。1 文に造語 2 個以上を強いていないか。lead の造語密度が最小か |
| R11 | ADR 番号・他 repo・evidence ファイルへの参照は**導線であって説明の代替ではない** — その参照を消しても文が意味を運ぶか。「（ADR-0012）」が文の唯一の根拠になっている箇所を列挙する |
| R12 | 内部史（version 番号・モデル交代・「7 → 2」型の変遷・「以前は」）は、読者の問いに答えるときだけ残っているか。答えない内部史は docs/ へ |
| R13 | 数値は README 内で読者が解釈できるときだけ置かれているか（閾値・効果量・ノイズ床の生値は docs/evidence へ） |
| R14 | Quick Start の前提（外部サービス登録・ハード要件・必要な鍵の種類）が README 内で説明されているか。「API key 不要」型の強い主張は、どの鍵のことかが読者に伝わる書き方か |

### R-D フロアと肥大（参照のみ — 判定器の固定コアには含めない）

フロア 5 要素の復元・偽装 llms-full.txt 化・図のテキスト等価は `../SKILL.md` と
`readme-reviewer` agent が正本。判定器は §E の `details_blocks` / `figures` を証拠として見るに
留め、これらを理由に単独で verdict を決めない（lens の重複を避ける — 2026-08-19 Codex 指摘）。

## §K 著者の実指摘から一般化した 6 問

| # | 質問 |
|---|---|
| K1 | **as-of 整合**: 「現在〜で動いている」「最新は〜」型の主張は、README に書かれた時点情報（version・日付）と釣り合っているか。古い事実を現在形で言っていないか |
| K2 | **継ぎ足し検出（節単位が主）**: release ごとに足された bullet が、重複・矛盾・同型反復（「〜 instrument — … (ADR-00xx)」が 5 連続 等）になっていないか。各節の小結論を順に並べたとき一本の線を成すか。**README は commit 数に比例して継ぎ足される**ので、この項を主力にする（CA README は 187 commit の累積で発症） |
| K3 | **主張の論理**: 場合分け・排他・数量を主張する文（「〜しかない」「必ず」「2 依存だけ」型）を全て抜き出し、各々に反例を 1 つ探してから Yes を出す。反例を潰す論が本文になければ No — 本文にない防御を判定器が自作して通さない |
| K5 | **目的の欠落**: 詳細（機構・実行条件・機能）に入る前に、読者が「この repo は何のためにあるか」を言えるか。what / how / who に答えて **why** だけ欠けていないか。**見出しの有無で判定しない**（「Why this exists」節が無いことは欠陥ではなく、目的が立つ前に詳細が始まることが欠陥）。道具でない repo（実験・観察装置）が「〜向けのツール」型の対象者文を持っていないか。外部 platform で動く repo は platform が目的か場かを区別しているか |
| K6 | **lead の約束の行き先**: lead が産物・実績（「履歴」「記録」「改正された」）を約束するとき、README から到達できる行き先（リンク・節・as-of 付きの数）があるか。「more than once」型のヘッジで数を避けていないか |
| K4 | **指示語・先行文脈依存の回収**: 「the instruments' first payoff」「上の ADR リンク」型の、前の節を読んでいないと回収できない参照を、初見読者が近傍で回収できるか |

## §A アンカー比較（張り付き回避）

必ず答える: 「このチェックリストを完全に体現した README と比べて、本稿が**劣る点はどこか**」
— 最低 1 点、最大 3 点。Publishable を出す場合でも埋める（空欄 = 判定の甘さのシグナル）。
**著者自身の他 repo README をアンカーに使わない**（同じ癖を基準に持ち込む）。

## §D ループ設計への制約

- **over-editing 禁止**: 改稿ループは上限 2 ラウンド。2 ラウンド目以降は voice の正規化ドリフト
  （企業 About 化）が始まる。Fix は span 単位の指摘のみで、全文書き直し案を出さない
- **章立てテンプレを「埋める」加筆を Fix に出さない**: 節が足りないことは欠陥ではない。
  読者の問いに答えない節があることが欠陥
- **評価は欠陥検出に限定し、文体の方向づけに使わない**（Content Integrity。judge の好みへの
  収束 = 平坦化 Goodhart を起こさない）
- **迷ったら Fix**。Publishable は earned な例外であって既定ではない

## 判定注意

- §E の件数だけで verdict を決めない（ADR 参照 28 箇所は証拠であって判定ではない — 28 箇所が全部
  導線として機能していれば Publishable でありうる）
- 迷ったときの dominant question: **「初見の読者の時間を尊重しているか」**（density over
  completeness）。網羅性は docs/ と llms-full.txt の仕事
