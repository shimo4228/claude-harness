# ADR-0040: `feat` × TDD を必須から条件付き発火へ降格 — 儀式でなく spec pinning が残る価値

## Status

accepted

## Date

2026-08-15

## Context

Chain Matrix は `feat` 種別に対し TDD を `Y`（必須）として運用してきた。RED（失敗する
テストを先に書く）→ GREEN（最小実装）→ REFACTOR の順序を、新機能では例外なく通す規約である。

きっかけは 2026-08-14 の外部 exploratory eval（agent loop 内の TDD を判定した小規模比較）で、
「TDD あり／なしで成果物の品質と mutation score に明確な差は出ず、トークンは 3 倍以上」と
報告していた。ただしこれは n が小さく一次ソース未読の 1 本であり、`rules/common/knowledge-staleness.md`
の基準では設計判断の根拠として弱い。**この ADR はその eval を根拠にしない。**

根拠は、TDD が買っているものを分解した結果である。

| TDD が買うもの | 現行世代で成立するか |
|---|---|
| 小刻みな検証で作業記憶の破綻を防ぐ | **しない** — モデルは仕様全体を保持したまま test と実装を一度に書ける |
| 段階的に設計を発見する | **しない** — 設計は Plan / plan mode 側に移っている |
| テストという資産が残る | する。ただし**順序とは無関係** |
| 実装を見る前に観測可能な振る舞いを確定させる | **する。むしろ強まっている** |

最後の 1 行だけが残る。LLM は自分が書いたコードに対するテストを、同一コンテキストで、
そのコードが通るように書く。「仕様を検証するテスト」でなく「実装を追認するテスト」になる。
実装者とテスト作者が完全に同一コンテキストである分、人間の後付けテストより構造的に強く出る。

したがって順序が効くのは、**実装がまだ存在せず、それに合わせて合理化する余地がない時点で
仕様を固定したい場合に限られる**。仕様が会話で確定していて実装が素直なケースでは、順序の
強制はコストだけを生む。

前例もある。`fix` × TDD は 2026-08-08（`befcf41`）に同型の降格を通しており、条件は
「再現手順が言語化できる不具合のみ」だった。今回は同じ考え方を `feat` に広げる。

なお 2026-08-15 に実施した skill-stocktake フルパスは、この問いに答えられなかった。
バッチは「記述が正しいか」を検証する装置で、「その方針が現行世代で妥当か」は原理的に
判定対象外である（`tdd` も `implementation-chain` も Keep のまま返った）。判定先も当初の
見立てと違い、`tdd` skill ではなく `implementation-chain` の Chain Matrix だった。

## Decision

1. **Chain Matrix の `feat` × TDD を `Y` から `C` へ降格する。** 発動条件は「観測可能な
   振る舞いを実装前に固定する価値がある場合」— ① 仕様が曖昧でテストを書くこと自体が
   仕様確定の作業になる ② 境界条件・エラー時の振る舞いが争点 ③ 既存挙動との互換性が要件。
   いずれにも当たらなければ `-`。判断に迷ったら `Y`。
2. **テストの要否は変えない。** 降格したのは RED→GREEN の**順序の強制**だけである。
   coverage の床（80%、critical path は 100%）は `rules/common/testing.md` が保持し、
   Verify が機械的に当てる。`skills/tdd/SKILL.md` にこの区別を明記した。
3. **Verify の逐次必須は維持する。** 「TDD は Plan の後、Verify は全レビュー後（この 2 つは
   逐次必須）」という記述を「TDD は発火する場合 Plan の後。順序として逐次必須なのは Verify のみ」
   に改めた。

## Alternatives Considered

### `Y` のまま据え置く

順序の必要性を示す一次記録がそもそも無い。現行の `Y` は ECC からの継承で、この harness で
効果を測ったことがない。「前からそうだった」以上の根拠がない規約を、コストだけ払って
維持することになる。**却下**。

### `tdd` skill 側を退役させる

TDD の手順自体は、条件を満たす場面では今も有効で、`references/example.md` の 5 ステップは
そのとき使う。skill は残し、発火条件だけを絞るのが正しい粒度。**却下**。

### 外部 eval を再現してから決める

n が小さく一次ソース未読の 1 本を再現するより、自分の repo で `skill-comply` を回して
実測する方が意思決定に効く。ただしそれは条件を絞った後でも測れる（むしろ `C` の発動条件が
妥当かを測る方が有用）。判断を先送りする理由にならない。**却下**。

### `-`（完全撤廃）にする

spec pinning の価値は残っており、仕様が曖昧な feat では今も順序が効く。撤廃すると
「実装を追認するテスト」を防ぐ手段が chain から消える。**却下**。

## Consequences

### Positive

- 仕様が確定している素直な feat で、順序強制のコストを払わなくてよくなる。
- 順序を通す場面が「仕様固定に効く場合」に限定され、規約の理由が説明可能になる。
- `fix` と `feat` の TDD 発火条件が同じ形（条件付き + 迷ったら Y）に揃った。

### Negative

- `C` の判定はメインループの判断に依存する。`Y` の一律強制に比べ、判断が甘い方向へ
  ドリフトしうる。歯止めは Verify の coverage floor だけになる。
- 「TDD は必須」という単純な規約が失われ、chain の説明がひとつ複雑になる。

### Neutral / Follow-ups

- 発動条件の妥当性は `skill-comply` で測れる。旧 `Y` 運用との比較データは無いので、
  取れるのは「条件を満たす場面で実際に発火しているか」まで。
- この判断自体も足場である（`rules/common/akc-cycle.md`「ADR も足場である」）。
  spec pinning の必要性が substrate に吸収されたら、`C` ごと再監査する。
