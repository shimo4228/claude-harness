hillclimb の failure mode（主題）: held-out に触れる、ground truth が手の届く所にある、不自然な跳ね上がりを信じる、信頼できない eval 上で登る、壁に当たって content を削り続ける、refusal を score に平均する（scrub 述語は score が出る前に事前登録）、ループ中の platform 変化、説明できない利得、1 case からの過一般化、束ねた変更の追跡漏れ、見えない小さすぎる変更、fluff の蓄積、state の喪失、off-limits の編集、予算の誤処理。

#### 1-E. 過学習 guard とその隙間（local read からの読み。引用以外は「official-procedure note の推論」）
- あるもの（case レベルの過学習）: 固定した層別 train / test、analyzer は train trace のみ、外側は score のみ、winner と headline は test、「train 上昇・test 平坦 → revert」、内容でなく振る舞いを一般化する steer、de-fluff、noise floor 前提と delta > floor の停止、CI 付き最終 delta と「noise 内なら merge しない」推奨、2 つ目の model での確認、held-out を開かない。
- 隙間（推論）: (1) **grader への過学習は split で防げない**: held-out も同じ grader を使うので、judge が表面 pattern を報酬すれば train も test も上がる。防御は「説明できる幅を超える跳ね上がり」の手 spot-check と、2–3 round 停滞後の Step 4.5「grader 不一致」bucket（事後発見）。(2) **analyzer は judge の推論を見うる**: train 行を grade dict 全体で受け取り、`explanation` は行の任意 field で、eval-audit §2 が「grader 自身の入出力」を trajectory に保存することを勧める。`explanation` が analyzer に届くかは明記なし。届くなら rubric が optimizer に露出する（推論）。(3) **test 上での選択が毎 round 起きる**: test score が best round を選ぶので headline は held-out 上で選択済み。3 分割（validation + 触らない test）は約 150 case 以上でのみ任意。(4) **cross-case metric では split が無効**（pairwise 順序・ranking は no-split・「directional」）。採点方式の選択が held-out guard の有無を決める。(5) **多重比較・round 数の補正の記述が無い**（K round を同じ test で選択）。(6) 途中で eval を変えるのは契約上禁止で、方式が誤りと分かった時点で払い済みの round が無駄になる。

#### 1-F. 継ぎ目（seam）と受け取り形式（official-procedure note の推論を含む）
- 外部の方式選択 step の差し込み位置は build-eval の中の 2 候補。**(a) Step 0 と Step 1 の間**: flow と出力形は分かったが入力は未承認。`expected` は採点器に従って決まる（literal target / baseline 応答 / case ごとの rubric 文）ので、sign-off 1 の後で方式を選ぶと承認済み入力が無効になり再承認になりうる（build-eval の順序に内在する潜在的な結合）。**(b) Step 2 の採点器 AskUserQuestion で "(Recommended)" として**: 内部の出力形ヒューリスティクスの代わりに推薦の出所にし、sign-off 2 は変えない（user は約 5 件の採点例を読む）。build-eval は「推薦先行」設計で AskUserQuestion が推奨を先頭に取るので摩擦が最小。
- **hillclimb に継ぎ目は無い**（eval を固定として扱い、「eval set と予算は user に戻らずに変えない」）。Step 4.5 が示す通り途中の grader 変更は全 variant の再採点と再開を伴う。よって検索は **build-eval の sign-off 2 の前に終える**。hillclimb 内では回せない。
- 受け取り形式: build-eval Step 2 は 4 型（programmatic / pairwise blind / pointwise rubric / human spot-check）で表せる提案を期待し、加えて含めた / 除いた基準、metric id と `kind`（binary / float / judge）と `better`、per-case の `grade`（bool / number / `{metric_id: number}`）、judge 方式なら judge model 選択と構造化出力 schema、`expected` の意味、pairwise なら凍結 ref の場所。4 型に収まらない文献の方式（set-level metric、ranking、calibration score）は `Variant.metrics`（summary のみ）か `metrics.md` 表にしか着地しない。根拠 / 出所（論文・as-of 日付）を置く field は `_state.json` に無い。CLI に入る lite builder は `metrics.md` も `narrative.md` も読まない（`build-report-lite.mjs` の grep では `results.jsonl` / `errors.jsonl` / `change.md` / `summary.json` / `traces/` / `_state.json` を読む）ので、full viewer 無しで耐久的に残せるのは user が直接開く sidecar file のみ。
- build-eval は既にタスク型で採点方式を選ぶか: **出力形に基づいて部分的に**。閉じた出力空間 → programmatic、環境に作用する agent → end-state programmatic + 趣味にだけ judge、比較の問い（移行・v1 vs v2）→ pairwise、baseline 無し / 絶対値が欲しい / 開放 → pointwise rubric、rubric が書きにくい → human spot-check、ラベル付き正負 → 混同行列。規則は「実際に測りたいものを測れる最安のもの」。**しない**こと: 文献・benchmark からタスク特有の方式を探す、タスク型別の judge 信頼性の根拠を出す、4 型の外の方式に言及する。妥当性機構は内部のみ（user が採点例を読む、eval-audit §4 の「人間ラベルと約 90% 一致」と known-negatives、oracle / null）。

#### 1-G. 人間 gate の順序（official-procedure note の F を統合）
① flow を決める（interview）② 既存部品の再利用 ③ 入力の出所・代表性・`expected` の provenance・PII / retention → **sign-off 1: inputs** ④ 副次 metric・混同行列・採点器の 4 択・judge model・基準の含む / 除く → 採点例 → **sign-off 2: grading method**（1 件の不一致でも iterate）⑤ runner の方式、`--approve-harness`（user のみ）⑥ eval-audit 事前確認 → 「N×R on model, ~Z min」→ **gate: yes**（ドルは聞かれた時だけ）⑦ baseline run、report 検証、commit の選択 ⑧ hillclimb: 実行可能 eval 確認、Step 0.5 の証明、goal + scope + off-limits + harness paths、停止条件 → **plan sign-off**、runner command の allowlist、任意の round 別 diff 承認、予算上限（聞かれた時）、harness 編集時の user 実行 `--approve-harness` ⑨ merge / no-merge は user（delta が noise 内なら merge しない推奨）。

#### 1-H. native eval は別の対象（local read）
skill-creator §5 `claude plugin eval <skill dir> --ablation with-without --runs 3` は **screening ablation**（その skill が振る舞いを変えるか。約 $1 / 5 分 / skill、2026-09-13 実測）。grader は `tool_used: Skill` の発火検出、isolation は plugin のみを読み込む（user の skill / agent / CLAUDE.md / memory は無し → 他 skill に委譲する skill は false negative）、tool trace は `--keep-temp` 無しで削除。ADR-0066 の記録（2026-09-15）: with 0.00/0.67/0.00 vs without 0.33/0.00/0.67、meanDelta −0.11（3 run は noisy）。`task-triage:81` は `claude plugin eval` が「存在したが gated」、ADR-0043:122 は org gate で実行不能だった時期があると記す。build-eval / hillclimb は held-out split と reporting を持つ最適化、§5 は go / no-go の screen。組み合わせられる（screen → optimize）が互いを呼ばない。

### 3. 先行ツール・framework（as-of 2026-10-06。prior-tools note）

1. **Anthropic「Define your success criteria / develop tests」**（https://platform.claude.com/docs/en/docs/test-and-evaluate/develop-tests、docs.anthropic.com は 301。要約経由全文。ページに日付なし）。対象・前提: 5 行の静的表 — 感情分類 → accuracy → exact match / FAQ bot → consistency → cosine sim（SBERT）/ 要約 → ROUGE-L F1 / customer service の tone → Likert 1–5 の LLM judge / 医療 chatbot の privacy → 2 値 LLM 分類（PHI か）。加えて採点方式の階層（code > LLM > human）、「生成と別 model を grader にする」、「quality より volume（多数の自動採点 Q が少数の人間採点 Q に勝つ）」、SMART な成功基準（例 F1 ≥ 0.85）。タスクで選ぶか: 5 例の例示のみで手順ではない。証拠: vendor の guidance / 意見。こちらとの違い: eval-search が拡張する vendor 公認の prior。「volume over quality」は `author-calibrated-eval`（blind read が ground truth）と緊張（Contradictions）。移せる: 3 段 ladder（exact / code → LLM → human）を既定の決定順に、表を方式 catalog の seed 行に。

### 4. 論文 → タスク型 × 方式の妥当性（as-of 2026-10-06。papers note）

読み取り深度の注意: 項目 1–9・11 の数値は小型 extractor が返したもので**逐語確認していない**（arXiv `html/` ページ本文には到達）。EvalGen（2）と self-preference（10）の abs ページのみ abstract が逐語。項目 12 は alphaxiv の overview のみ（arXiv 本文でなく、最弱）。plan に hard number として載せる前に再読すること。judge 精度の数値は全て 2024–2025 世代の judge（GPT-4o / Claude-3.5-Sonnet / o3-mini / Llama-3.x）のもので、タスク別の数値は数か月で陳腐化する。

1. **Adding Error Bars to Evals**（Miller、arXiv 2411.00640v1、2024-11-01、stat.AP。https://arxiv.org/html/2411.00640。extractor 経由、本文到達）。主張: SEM（CLT、bootstrap でない）を報告、2 値は SE = sqrt(p(1-p)/n)、問いが cluster するなら cluster SE（DROP の例で cluster SE 1.34 vs naive 0.44 = 3.05 倍）、model 比較は対の差 SE_paired = sqrt(Var(sA-sB)/n)、1 問あたり K 回再サンプルで条件付き分散を削減（K=1→2 で 1/3、K=4 で 1/2、難度一様の仮定）、分散を下げるために temperature を 0 にしない（分散が条件付き平均へ移り最小分散が 3 倍になりうる）、検出力式 n = (z_{a/2}+z_b)^2 (omega^2 + sigmaA^2/KA + sigmaB^2/KB) / delta^2、例（omega^2=1/9, delta=0.03, alpha=0.05, beta=0.20）で n ≈ 969、「新しい eval は 1,000 問以上」。papers note の再計算: (1.96+0.84)^2·(1/9)/0.03^2 = 968 で整合。前提: benchmark 規模（数百〜数千問）、model 対 model、問いの分散は超母集団からの無作為抽出。証拠: 統計理論 + 公開 benchmark の worked example（prompt 調整の実証研究ではない）。こちらとの違い: 単独著者の harness は 20–100 case で、対象は model 対でなく prompt / skill の variant 対。n ≥ 1000 は delta = 3 pt を検出するためで、小 set では大きな delta しか検出できない。移せる（papers note の算術、omega^2 = 1/9・sigma 項なし・alpha .05・power .8 の例を使用。omega^2 は著者自身の対の差から再推定が要る）: 検出可能 delta ≈ 2.8·sqrt(omega^2/n) → n=30 で約 0.17、n=50 で約 0.13、n=100 で約 0.09、n=200 で約 0.066。n=50 では約 13 pt 超の対の差しか noise と区別できない。そのまま移る規則: (a) A と B を**同じ item** で評価し対の差で解析、(b) n と SE を全 score の隣に報告、(c) item が同一元 case の variation なら cluster-aware SE、(d) temperature は本番値のまま K>1 で再サンプルし T=0 にしない。なお adversarial note の F5 は同論文を **abstract のみ**（PDF は binary、数値は未読）で扱う（read depth の差は Contradictions に記載）。
2. **Who Validates the Validators? / EvalGen**（Shankar, Zamfirescu-Pereira, Hartmann, Parameswaran, Arawjo、arXiv 2404.12272v1、2024-04-18、cs.HC。https://arxiv.org/abs/2404.12272。**abstract のみ（逐語）**、PDF は binary で参加者数・タスク詳細・alignment 指標は未取得 — 研究規模を引用しない）。abstract: LLM 生成 evaluator は「評価対象の LLM の問題を全て継承し、さらに人間の検証が要る」。EvalGen は mixed-initiative: LLM が基準と候補 assertion（Python 関数か LLM-grader prompt）を提案、人間が出力の部分集合を採点、人間の採点との alignment で実装を選ぶ。定性研究が alignment の主観性と反復性を強調し **criteria drift** を命名: 「基準が無いと出力を採点できないが、出力を採点することが基準を定義する」。adversarial note の F8 は同論文を snippet で扱い UIST 2024 と記す。前提: LLM pipeline 構築者の定性 user study、evaluator = 基準ごとの assertion、人間の thumbs との alignment。証拠: HCI 定性研究 + tool 設計（benchmark でない）。こちらとの違い: harness の著者は単独の user かつ単独のラベラーで、まさに EvalGen の設定。検索で方式を選んでから出力を見る skill には直接の警告。移せる: eval 仕様は著者が実出力を採点する前に凍結できない。skill に「著者が約 N 件を採点 → 基準 / rubric を改訂して再検証」step が要り、rubric は版管理する（基準は drift する）。採点サンプルの正確な N はこの source では支持されない。
3. **JudgeBench**（Tan et al.、arXiv 2410.12784v2、2025-04-05、https://arxiv.org/html/2410.12784。extractor 経由、数値は逐語未確認。ICLR 2025 は note の記憶で fetch では未確認）。MMLU-Pro / LiveBench / LiveCodeBench 由来の 350 対（Knowledge 154 / Reasoning 98 / Math 56 / Coding 42）。各対は GPT-4o の正解 1 + 不正解 1（ground truth は人間選好でなく正誤）。最良は o3-mini (high) の 80.86%、Claude-3.5-Sonnet 64.29%、random 50%、Arena-Hard-Judge prompt（GPT-4o）56.57%、vanilla prompt 50.86%、fine-tuned judge の大半は random 未満（PandaLM 13.14%）、Skywork reward model は例外で Claude-3.5-Sonnet に並ぶ、judge の精度は同 model の solver 精度に「近く追随」。前提: 客観的に検証できる難問の pairwise judging、2024 中〜2025 初の世代の judge。証拠: benchmark。こちらとの違い: harness の対象は prompt / skill / agent 出力で客観検証できないことが多く、現行世代の judge は試験された世代より強い。ただし構造的な所見は残る: 正解を作るのが難しいタスクでは judge は自分で解く能力程度にしか判定できない。移せる: 検証可能な ground truth（コードが走る、数学の答え、完全一致する field）があるなら judge でなく**検査を実行**する。judge は「検証が解くより易しい」かつ「judge が generator より強い」場合に限る。
4. **Judging the Judges**（Thakur et al.、arXiv 2406.12624v6、2025-08-18、https://arxiv.org/html/2406.12624。extractor 経由、数値は逐語未確認）。TriviaQA 上で judge 13 × 被験 model 9。人間注釈つき 400 問（3 人の多数決。extractor は「1,200 questions」と書いたが曖昧で、1,200 注釈の可能性）。**percent agreement は歪み情報に乏しい**: 一致率の高い judge でも人間採点と 10–20 pt ずれうる。Scott's pi の方が judge を分離する。被験 model の ranking: lexical な「contains」baseline は人間と Spearman 0.99、Mistral 7B 0.98、GPT-4 Turbo 0.98 — つまり弱い judge と regex が最良 judge と同程度に model を ranking できる一方、絶対 score の整合は悪い。脆弱性: 寛容バイアス（P+ が 0.5 を大きく超える）、小さい judge は参照順序に敏感、指示が長いと整合が落ちる、「Yes」「Sure」のようなダミー回答を受理することがある。推奨: percent agreement と Scott's pi と質的 error analysis を併記。前提: 参照回答つきの短い事実 QA。証拠: 人間注釈つきの経験的 meta-eval。こちらとの違い: 単一のタスク型（参照つき短答）で、開放的な文章には何も言わない。移せる: 参照つき短答はまず最安の check（正規化一致 / contains）。judge の価値は絶対 score の精度であり、hill-climbing が要るのは ranking。judge の検証は偶然補正した一致（Cohen kappa / Scott pi）で、percent agreement でなく。judge にダミーの「Yes」を食わせて試す（dummy-answer probe）。
5. **LLMs instead of Human Judges? / JUDGE-BENCH**（Bavaresco et al.、arXiv 2406.18403v3、2025-06-02、https://arxiv.org/html/2406.18403。extractor 経由、数値は逐語未確認、judge は 2024 世代）。11 LLM × 20 NLP dataset、7 万超 instance（MT / 対話 / 要約 / 毒性 / 推論等）。結論（引用）: 「Models are reliable evaluators on some tasks, but overall display substantial variability depending on the property being evaluated, the expertise level of the human judges, and whether the language is human or model-generated.」categorical なタスクの平均 Cohen kappa は 0.28（GPT-4o）/ 0.28（Llama-3.1-70B）/ 0.24（Mixtral-8x22B）、graded なタスクの平均 Spearman は 0.50 / 0.43 / 0.44。高い一致: 指示追従（LLMBar-natural 0.84 GPT-4o）、数学推論（ROSCOE-GSM8K graded 0.82）、レシピ生成（0.78）。低い: 毒性・安全（DICES で負の相関、−0.24 まで）、医療安全（約 0）、対話の engagingness（低）、MT 品質（WMT23 0.22 GPT-4o）。非専門家の注釈者との方が専門家より整合し、機械生成より人間が書いた text の方が整合する。CoT の効果は一貫しない。前提: 元の注釈 guideline での zero-shot judge、人間 = 既存 dataset の注釈者。証拠: 大規模経験的 meta-eval（今回見つけた「タスク型別」の証拠で最強）。こちらとの違い: crowd 注釈の公開 dataset で、著者自身の選好ではない。著者の taste は「専門家」注釈者に当たり、そこでは一致が低かった。移せる（決定規則）: タスクの性質が judge の妥当性を決める。指示追従・形式・数学 → judge か programmatic が妥当、主観的品質（engagingness、MT の流暢さ）と安全 → 著者自身の採点に対する較正なしで judge を信用しない、LLM 生成 text の judging は人間が書いた text より難しい（harness の場合）。論文自身の推奨「人間の判断に対して慎重に検証してから使う」は skill が符号化すべき gate。
6. **RewardBench 2**（Malik et al.、arXiv 2506.01937v2、extractor 報告で 2026-04-23〔未検証、現在 2026-10 と整合〕、https://arxiv.org/html/2506.01937。extractor 経由、領域別の judge 数値は未取得）。1,865 prompt、best-of-4（正 1 + 誤 3）、6 領域: Factuality 475 / Precise IF 160 / Math 183 / Safety 450 / Focus 495 / Ties 102、約 70% が WildChat の未見の人間 prompt。最良は Skywork-Reward-V2-Llama-3.1-8B の平均 84.1%、RewardBench-1 の上位 model は RB2 で ≥20 pt 低い。下流との相関: best-of-N で Pearson r = 0.87、RLHF/PPO では相関が限定的で性能は「すぐ飽和」、off-policy / OOD の reward model は劣化。classifier RM と、2 モード（4 つから最良を選ぶ / 絶対評価）で使う生成 judge を比較。前提: 固定の best-of-4 での reward model / judge 精度と、best-of-N・PPO の下流試験。証拠: benchmark + 下流相関。こちらとの違い: 訓練用 reward model の話で prompt variant の judging ではなく、移転は類推。eval set 上の hill-climbing は選択（best-of-N）に最も近く、そこでは benchmark 精度が下流 r = 0.87 を追跡した。「飽和 / OOD で劣化」は、ある分布で検証した judge が調整後 prompt の変化した出力に移転しない警告。移せる（弱い）: judge は最初の出力だけでなく**最終候補の出力**で再検証する。領域分割（factuality / precise IF / math / safety / focus）は「どの方式か」表のタスク型 checklist として使える。
7. **How to Correctly Report LLM-as-a-Judge Evaluations**（Lee, Zeng, Jeong, Sohn, Lee、arXiv 2511.21140v2、2026-01-04、ICML 2026 poster、https://arxiv.org/html/2511.21140v2、venue page https://icml.cc/virtual/2026/poster/63607 は検索に出たが未開封。extractor 経由、数値は逐語未確認）。感度 q1・特異度 q0 の 2 値 judge の生 accuracy は偏る。plug-in 補正 theta = (p + q0 − 1)/(q0 + q1 − 1)、CI は test-set と較正 set の不確実性を含む（小標本向けに「成功 2・失敗 2 を足す」型の delta 法調整）、較正サンプルの適応配分 m0 ≈ (1/p − 1)·sqrt(kappa)·m1、kappa = (1−q0)/(1−q1)。命題 6.1: judge ベース推定が人間のみより分散が小さいのは judge の q ≥ 1/2 + 1/(2√2) ≈ 0.854 かつ真の accuracy が 0.5 近傍の帯にある時のみ。較正の目安: q0=0.7・q1=0.9 で CI 長 <0.1 に約 200 の較正例。Chatbot Arena で GPT-4.1-mini を judge に: coverage 95–99%、CI 長 0.178–0.267。Monte Carlo は n=1000 test・m=200 較正。前提: 2 値の正誤 judgment、較正 split の人間ラベルは信頼でき、較正と test で混同行列が安定。証拠: 統計手法 + simulation + benchmark 実験 1 件。こちらとの違い: 較正 200 ラベルは単独著者がタスクごとに手でラベルする量を超える。30–50 ラベルでは CI が広く、論文自身の bound でも judge が効くのは q ≥ 0.854 の時のみ。移せる: (a) judge の生 pass-rate は accuracy ではない — skill が絶対 judge score を報告するなら著者ラベルに対する感度 / 特異度を併記、(b) A vs B の ranking（絶対 score でなく）では補正の影響が小さいので、ranking の主張の方が level の主張より安全、(c)「著者ラベルの標本で一致が高い（q ≳ 0.85）時のみ judge を使う」という定量 gate には理論的根拠がある（ただし 2 値 judge の分散の議論のみ）。
8. **LLM as Judge Won't Beat Twice the Data**（Dorner, Nastl, Hardt、arXiv 2410.13341v4、2026、https://arxiv.org/html/2410.13341。extractor 経由、venue〔note の記憶で ICLR 2025〕は未検証）。frontier（judge の ground truth との一致 ≤ 評価対象 model 自身の accuracy）では、judge による debias は必要な人間ラベルを 2 倍超には減らせない（定理 6: rho^2 ≤ 0.5 ⇒ efficiency ≤ 2）。MMLU と MT-Bench で経験的に確認（GPT-4 judge の約 84% accuracy で Claude を MMLU 上で評価: efficiency は 2 倍未満）、2 倍超になるのは SOTA model が弱い model を judge する時のみ。前提: 2 値の正誤、judge は proxy score、ground-truth ラベルあり。証拠: 定理 + 経験的確認。こちらとの違い: judge が被験系より優れないと仮定。target と judge に同じ top model 系列を使う harness では真、強い judge が弱い / 小さい model の出力を採点する場合は偽。移せる: ラベルが乏しい単独著者では、judge と target が同等の強さなら judge が買えるのは最大約 2 倍の実効サンプル — 25 を手でラベルして judge を使うと約 50 の価値で 500 ではない。「サンプルが増えるから」を judge の正当化に使わない。
9. **Pairwise or Pointwise? Feedback protocols and bias**（arXiv 2504.14716v2、2025-08-21、https://arxiv.org/html/2504.14716。extractor 経由）。注入した distractor（断定調・冗長・追従）の下で pairwise の選好は「約 35%」で反転、絶対 score は「9% のみ」。同質の応答で絶対 score は 84.6–93.2% で同点（tie）、pairwise の tie は 2.4–7.3% のみ。pairwise の精度は distractor の低 severity で劣化、絶対は安定。推奨（extractor）: 客観基準（指示追従・正しさ）は絶対 score。前提: 開放重み judge（LLaMA3.2-3B / LLaMA3.3-70B / Qwen2.5-3B / Qwen2.5-72B、logit アクセス）、distractor は合成、客観基準のタスク、dataset は IFEval-TweakSet（400 prompt、検証可能な規則）と MT-Bench（80 の multi-turn 問、1,689 の Turn-1 応答）。証拠: 統制実験。こちらとの違い: frontier の閉じた judge は無し。逆の弱点（絶対 score は同点が多く解像度が低い）がまさに小 n の hill-climbing に効く（近い variant を弁別したい）。移せる: pairwise は解像度を買う代わりに style バイアス（長さ・断定性）を払う。客観基準の無いタスク向けで、order-swap と長さ制御を伴う。客観基準には絶対 / 2 値。「pairwise は悪い」とは読まない。トレードオフであり、extractor の「推奨」は客観基準タスクに限る。
10. **Self-preference bias**（Wataoka, Takahashi, Ri、arXiv 2410.21819、v1 2024-10-29 / v2 2025-06-21、https://arxiv.org/abs/2410.21819。**abstract のみ（逐語）**）。定量指標を導入、GPT-4 は「有意な」自己選好を示す、仮説は LLM が perplexity の低い（なじみのある）出力を好むこと、LLM は人間評価者より「自己生成かを問わず」低 perplexity の出力に有意に高い評価を与える。前提: 対話 system の評価、GPT-4 を judge に。こちらとの違い: harness は Claude model の出力を持つ prompt を hill-climb し、（通常）Claude で judge する — 同系列 judging が既定のケース。移せる（弱い、abstract のみ）: generator と judge に同じ model（できれば同じ系列）を使わない。避けられないなら勝ち variant に著者の spot 採点を足す。原因が同一性でなくなじみ（perplexity）なので、似た別系列に替えても部分的にしか効かない。
11. **CheckEval**（Lee et al.、arXiv 2403.18771v2、2025-03-16、venue は extractor が示さず。https://arxiv.org/html/2403.18771v2。extractor 経由）。品質次元を boolean の yes/no 問に分解（種の問いは人間が書き、LLM が多様化・精緻化し、filter する）、score は「yes」の割合。SummEval で平均 Spearman 0.48 vs G-Eval（Likert）0.40、Topical-Chat 0.56 vs 0.43。評価者間一致（Krippendorff alpha / Fleiss kappa）は大きい model で最大 0.67 vs G-Eval 0.01–0.51（SummEval 0.05–0.16）。12 の evaluator LLM（7B–123B、GPT-4o を含む）。前提: 2 タスク（要約・対話）、2024 世代の judge、公開 dataset の人間注釈、手動構築の checklist。証拠: 手法の著者自身による benchmark 相関研究（独立再現は今回見つからず）。こちらとの違い: 著者自身の手法 vs 弱い Likert baseline で、pairwise judging や手書き rubric ではない。extractor が報告した限界: 要約と対話のみで、部分ごとに強弱がある長い出力では yes/no が崩れる、checklist の手動構築。移せる: 2 値に分解した基準は judge 間一致が上がり、監査・較正がしやすい（基準ごとに感度 / 特異度を持てる。項目 7・12 と整合）— TICK（arXiv 2410.03608、検索結果にのみ出て未開封）と整合。「checklist > Likert」の証拠はその 2 タスクと著者自身の実験に限る。
12. **Agreement Metrics for LLM-as-Judge Evaluation**（Rao, Callison-Burch、arXiv 2606.00093、extractor は「Submitted 31 Jul 2026」と述べるが ID 接頭辞は 2026-06 を示唆 — 日付は未検証。https://www.alphaxiv.org/abs/2606.00093。**alphaxiv の overview のみで arXiv 本文ではない。最弱 — pointer 扱い**）。同じ verdict でも尺度・保持 case・棄権 / 無効の扱い・item と rubric 基準のプールで一致の数値が大きく変わる。2 値 verdict では Pearson r / Spearman rho / Kendall tau-b / phi / MCC は数学的に同一。Cohen kappa はラベル不均衡下で accuracy が高くても低くなる。judge が棄権するなら同定境界を報告、混同行列と基準別の内訳を出す。新実験は不明の報告ガイダンス。移せる: skill の「judge 検証済み」gate は基準ごとの混同行列（著者ラベル vs judge）と無効な judge 出力の扱いを保存し、次セッションで「一致 = X」が再現できるようにする。

出典のある標本サイズ / 妥当性 gate:
- 同一 item の対の比較、n と SE を報告（項目 1）。項目 1 の例の分散下で n=50 の検出可能 gap は約 13 pt（papers note の算術）。
- 絶対 score に judge を使うのは、著者ラベルでの感度 / 特異度を測った時のみ（項目 7: 人間のみより分散を下げるのは q ≥ 約 0.854、CI < 0.1 に約 200 ラベル〔q0=.7 / q1=.9〕）。n≈30–50 ラベルでは区間が広いと予想。
- frontier では judge は最大約 2 倍のラベル効率（項目 8）。
- 基準は、著者が実出力を採点した後でのみ凍結。rubric は版管理（項目 2）。

失効条件（papers note）: judge 精度の数値は全て 2024–2025 世代の judge のもの。構造的な所見（対の統計、kappa vs percent agreement、self-preference の機構、2 倍 bound、criteria drift）は leaderboard 数値より陳腐化しにくい。再確認条件: 2026 年後半に現行 Claude judge でコード / 文章を扱う meta-eval が出ること。無効化条件: 現行世代の judge が対象タスクの著者自身のラベル標本で一致 ≥ 0.85 に達すること。

#### 5-H. 代替の枠組み（adversarial note の合成。単一 source のものではない）
1. **climb でなく gate**: 構築した eval を手編集した prompt の regression gate として使い（Willison の結論）、検索 step は人間が採用する評価方式を提案するだけにする。optimizer-on-judge のループを丸ごと除ける。
2. **梯子つき climb**: iteration を有界にし、validation での対の改善が noise margin を超えた時だけ受理、最終 test は 1 回、人間が diff と 3–5 出力を読む。
3. **voice タスク**: judge score で登らない。決定的な proxy（長さ比、禁止句 list、原文との overlap）を guard 制約にし、受理規則は人間の pairwise check。
4. **機構が先**: F1 の唯一の持続的な利得は content の書き換えでなく構造変更だった。規則を蓄積する前に構造的な編集（format・順序）を提案する。F1 と F2 は規則の蓄積が regression の源という点で一致。

失効条件（adversarial note）: この分野は週単位で動く。F1 と F7 は 5–6 週前のものなので、2026-11 頃以降に判断で頼る前に再確認する。

## Contradictions

食い違いごとに「どちらの根拠が強いか」を添える。統合者の判断は「（統合者の読み）」と明記。

1. **build-eval の「連続 measure を優先 / score と reasoning を返す」 vs `llm-as-judge` の「score を集約しない・2 値 + 名前付き verdict」**。
   - 一方: build-eval Step 2（e）「トレードオフには硬い閾値より連続 measure」と Step 2（c）③ pointwise rubric（local read、公式仕様。経験的根拠の記述は無し）。Anthropic develop-tests の「tone → Likert 1–5 の LLM judge」（要約経由全文、vendor guidance）も同じ側。
   - 他方: `llm-as-judge`（local read、harness 規則）。支持する外部証拠は CheckEval（要約経由 extractor、2 値分解 0.48 vs Likert の G-Eval 0.40、一致 alpha 最大 0.67 vs 0.01–0.51。**著者自身の手法・要約と対話の 2 タスクのみ**）、PROCTOR（FULL*、rationale を score の前に +9.3%、現場報告 1 件）。
   - 統合者の読み: 公式側も同じ文書内で「rubric は具体的に検証できる主張で 1–5 尺度でない」（build-eval Step 2（c）③）、eval-audit §4「atomic checks over holistic scores」と言っており、衝突は「連続 measure」をどこで使うか（トレードオフ基準の集約）に狭まる。調停案: case 内は `{check_id: 0/1}` + 2 値 verdict、case 間の pass-rate・CI は禁じられた集約ではない（official-procedure note の読み）。1–10 点や rubric 平均を出す外部方式は 2 値チェックへ翻訳するか、衝突を明示して持ち込む。証拠の強さは、2 値分解側の外部証拠は限定的（2 タスク、著者自身）だが、反対側に実験的根拠は見つかっていない。
2. **「pairwise > 絶対」（caller が挙げた earlier report の合意）vs pairwise は distractor 下で約 35% 反転**。
   - earlier report 自体は 4 本の notes に含まれず、その出典・read depth は本統合では確認できない（caller 提供として扱う）。build-eval は比較の問い（移行・v1 vs v2）で pairwise を ② に置く（local read）。
   - 反対側: arXiv 2504.14716v2（2025-08-21、extractor 経由、統制実験）— distractor（断定調・冗長・追従）下で pairwise は約 35% 反転 vs 絶対 9%。ただし**開放重み judge（3B–72B）・合成 distractor・客観基準のタスク**で、extractor の「絶対 score を推奨」は客観基準に限る。逆の弱点: 絶対 score は同質応答で 84.6–93.2% が同点 → 小 n の hill-climbing の解像度が低い（pairwise の tie は 2.4–7.3%）。
   - 統合者の読み: トレードオフで、どちらも全面的には勝たない。客観基準 → 絶対 / 2 値、客観基準なしの 2 variant 比較 → order-swap・長さ制御つき pairwise（build-eval は blind・ランダム化・`tie` / `both_bad` を持つが長さ制御の記述は無い）。Judging the Judges（extractor、TriviaQA 短答）は、hill-climbing が要る ranking では安い judge / regex でも足りる一方、絶対 score の整合は悪いと示し、方向としては Lee et al.（2511.21140、extractor）の「ranking の主張は level の主張より補正に頑健」と整合する。強い根拠は 2504.14716 の統制実験だが frontier の閉じた judge を含まない。
3. **hillclimb の train / test split vs PROCTOR の「holdout 4–8 は noise」と「test 上での選択」**。
   - hillclimb（local read）: 既定は `tags[0]` で層別した随機 split（baseline score では層別しない）、test score が winner と headline を決める、小 set / cross-case metric なら split せず「directional」、3 分割は約 150 case 以上のみ任意、多重比較補正の記述なし、停止条件は delta > noise floor / K≥3 の平坦 round / guardrail 後退（train か test かの明示は notes に無い）。build-eval の case 数は 15–100。
   - PROCTOR（FULL*、現場報告）: 19 case の holdout では train と並行、**4–8 case では測定 noise が支配**、**pass/fail 比で層別して 1 回 split**（hillclimb の「baseline score で層別しない」と逆）、停止は **train** が 3 iteration 改善しないこと、test は scalar のみ。Dwork / Blum-Hardt（snippet、理論）: 適応的な holdout 再利用は過学習、新しい最良は margin 超えでのみ受理、最終 test は 1 回。Willison F2: train 90 → 95 / test 95 → 85（test 10 問）— ただし 1 問 5–10 pt で gap 単独は noise 内（adversarial note の推論）、重みは trace から辿れた規則衝突。
   - 食い違い: build-eval が許す 15–100 case を split すると test は一部になり PROCTOR の noise 域に入りうる（split 比率は notes に無く、test の件数は統合者が算出していない）。hillclimb は test 上で毎 round best を選ぶので Ladder が警告する適応再利用に当たる。stratification の基準も逆（tags vs pass/fail 比）。
   - 強い根拠: 「4–8 は noise」「test 上選択」は現場報告 1 件 + 理論 snippet で、hillclimb の設計は公式仕様。どちらも実験的な決着は無い。実務上は skill 側で「best round の受理は incumbent を noise margin 超えで上回る時のみ、最終 test は 1 回」を足す設計余地がある（adversarial note の guardrail 一覧より）。
4. **AutoMetrics の「ラベルが先」/ EvalGen の criteria drift vs 方式が先の plan**。
   - AutoMetrics（abs 要約経由全文、実験節は未読）: 方式（metric）の選択基準は人間ラベルとの相関なので 100 未満のラベルが先。hamelsmu: 実 trace の error analysis が先で、失敗モードごとに evaluator を選ぶ（要約経由全文、実践者意見）。EvalGen（abstract 逐語）: 基準は著者が実出力を採点する前に凍結できない。
   - 本 plan: 検索 → 方式選択 → build-eval の順（方式が先）。build-eval 自身も入力 sign-off 1 → 採点方式 sign-off 2 の順で、`expected` が採点器で決まるので潜在的な結合がある（official-procedure note）。
   - 調停の材料（統合者の読み）: build-eval Step 2 は sign-off 2 の前に約 5 件の採点例を user に読ませるので、「方式は候補として先に出し、著者の実出力の採点で較正する」位置（継ぎ目 b）なら criteria drift を一部吸収できる。AutoMetrics の検索・生成フェーズがラベル無しで動くかは未確認（Still unknown）。強い根拠: criteria drift は abstract 逐語の HCI 研究、ラベル先は AutoMetrics 論文の設計で証拠の種別が違う。
5. **build-eval の consent は「時間のみ」vs harness の課金 gate**。
   - build-eval: consent gate は「N cases × R reps on model, ~Z min」で yes。ドルは聞かれた時だけ。Step 2 / Step 3 の pilot は有料で consent gate より前に走る。hillclimb の総 cost も聞かれた時のみ、予算は「壁でなく guide」。`--approve-harness` と runner command の allowlist は user が出す（local read）。
   - harness `boundary.md`: 課金は人間に渡す。
   - 帰結: skill が課金承認を持たなければ公式 flow の途中で未承認の有料呼び出しが走る。wrapper は Step 2 pilot の前にドル建て承認（case 数・rep 数・model・judge model・概算上限）を足す必要がある。さらに判断が要る未確認点: scaffold は Messages API client（API key 課金）を使うので、`claude -p` のサブスク課金の話（memory の `claude-p-subscription-billing-exposure-2026-06`）と別経路になる。確認は未実施（Still unknown）。
6. **Anthropic「volume over quality・生成と別 model を grader に」vs `author-calibrated-eval`（taste は著者の blind read が ground truth）**。
   - Anthropic develop-tests（要約経由全文、vendor guidance、日付なし）の「多数の自動採点 Q が少数の人間採点 Q に勝つ」。`author-calibrated-eval`（local read）: 2026-09-23 の実測で Opus judge が情報密度の高い草稿を両順序で選び、著者は短い方を選んだ。
   - 外部の裏づけは後者側: JUDGE-BENCH（extractor）で主観・安全の次元は一致が低く、LLM 生成 text の judging は人間が書いた text より難しい。Tutone et al.（abstract + snippet）で LLM judge が AI 生成の物語を好む。Dorner et al.（extractor）で target と judge が同等の強さなら judge は最大約 2 倍のラベル効率。
   - 強い根拠: 後者（ローカル実測 + 複数の外部 meta-eval）。Anthropic の表は 5 例の例示で手順ではない。
7. **eval-audit §4 の「人間ラベルと約 90% 一致」（percent agreement）vs 偶然補正した一致 / judge の検証法**。
   - eval-audit（local read）: clear-cut な case で約 90% を大きく下回れば judge prompt を直す。Judging the Judges（extractor）: percent agreement は歪みうる（高一致でも 10–20 pt ずれうる）、Scott's pi / kappa を併記。Lee et al.（extractor）: q ≳ 0.854 の判断。`measurement-discipline` 原則 9: AUROC / precision vs 基準率。
   - 統合者の読み: 公式の約 90% は clear-cut case に限った閾値で、偶然補正と基準率の扱いを規定しない。harness 側の原則 9 が具体形を持つので、skill は audit step で原則 9 を引き、混同行列を基準ごとに保存する（papers note 項目 12 の pointer）。
8. **build-eval の judge model 選択（haiku-4-5 / sonnet-5-5 / opus-5-5、provider 固定）vs self-preference の別系列 judge 推奨**。
   - build-eval: 被験 model は judge にしない、judge 呼び出しは同じ provider の client・model-ID 形式（local read）。Anthropic develop-tests: 生成と別 model を grader に。Wataoka et al.（abstract 逐語）: 原因は identity でなく perplexity（なじみ）で、似た別系列に替えても部分的にしか効かない。Panickssery et al.（snippet、2024 の GPT-4 / Llama 2 世代）: 自己選好は因果的、別系列 / blind の対処は adversarial note の推論。
   - 帰結（統合者の読み）: build-eval の選択肢は構造的に同系列（Claude）で、別系列 judge は公式 flow では作れない。緩和は被験と別 tier の judge と、勝ち variant への著者 spot 採点（papers note 項目 10 の移せる部分）。現行 Claude 組での自己選好の強さは未確認。
