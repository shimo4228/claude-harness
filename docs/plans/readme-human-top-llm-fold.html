readme-writer の README を人間の上と LLM の下に分ける

Why · 6 件 本当に人間の読むことを意識したREADMEはキャッチコピーのようなもので三行くらいで機能を説明してあとは摩擦の解消に費やされているように思う。記事とREADMEは全然性質が違うな READMEはここにきて人間読者が増えだしたから、ちょっと前提が変わったな。以前はLLM検索のみだったから むずかしいね。LLMにはできるだけ情報を与えた方がいいしな readme-writerの改修をplanにして。 冒頭三行でわかるはわたしのレトリックだから三行に固執しないでね。あとREADMEの構造を変に縛るのはよしてね。今回のことで、人間向けのREADMEとLLM向けのDetailsに使い分けができたことが、いちばんの収穫なんだから。 取得できた 5 回（ChatGPT / Claude.ai / Grok / Qwen / Gemini 3 回目）は V・D（
）・T（約 2.6 万字の末尾）をすべて ○ … Grok は初回取得で README が切れ、残りを自分で取りにいった

訪問者は冒頭の短い段落で、何をするものか分かる。

何をするものかを言う。行数は決めない。 LLM 向けの情報は全部ここ（claim 3）。

冒頭の概要図は残しますか。

見える本文は、何をするかと摩擦の解消に使う。

判定器は、冒頭の段落だけで何者か言えるかを問う。

冒頭の後は、使い始めの摩擦を消すことに使う。

LLM 向けの情報は、末尾の畳んだ節に全部ある。

送信内容や限界の説明は、どこに置きますか。

フロアの規則を「畳んだ節に置く」に反転する。

検査表の F1 と F3 を、畳んだ節の前提に替える。

README が長すぎると、証拠と判定器が知らせる。

長さの上限はどう扱いますか。

readme_sections.py:200 · details_blocks() の隣に置く

検索の断片に出る About も、冒頭と同じ主張になる。

共有：判断は ADR に残し、skill の改修は skill-creator を通す。

実行者の決定：誰が作りますか。

変えないもの：記事の流れ・既存 README・AI 専用の文書。

  • 記事（writing-ecosystem）は変えない。記事と README は性質が違う。
  • 既存の README の書き直しはしない。この改修の後に repo ごとに行う。
  • llms-txt-writer と AGENTS.md は変えない。llms.txt は補助のまま。
  • 描画の判定（§V、ADR-0088）と主張の照合（§C）は変えない。
  • note・dev.to・Zenn での畳み構造の実験は、記事の側の別の作業にする。
