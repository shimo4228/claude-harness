# ADR-0029: skill-comply のシナリオを並列実行し、進捗を stderr に移す

## Status

accepted

## Date

2026-08-01

## Context

2026-08-01 の実運用（Contemplative Agent 側のセッション）で skill-comply に 2 つの問題が出た。

### 1. 直列実行

`scripts/run.py` は 3 つのシナリオ（supportive / neutral / competing）を 1 本ずつ順に回す。
各シナリオは丸ごと 1 回の `claude -p` 実行で実測 2 分以上、採点の LLM 呼び出しが続いて
全体 15〜30 分規模。`results/implementation-chain.md` を見る限りこの規模は常態だった。

3 つのシナリオは互いに独立している。別プロンプト・別 sandbox・別プロセスで、
共有する可変状態は無い。採点（`grade`）ももともとシナリオごとのループの中にある。

### 2. 進捗が見えない

`| tail -40` を通して起動したところ、30 分近く 1 バイトも出なかった。
「stdout がパイプ越しだとバッファされる」という仮説が立ったが、切り分けたところ
**仮説は当たっているが、観測された症状の原因は別**だった。実測 3 本:

| 実測 | 結果 |
|---|---|
| `print("A"); sleep(3); print("B")` をパイプへ | 2 行が同時に到着 = ブロックバッファされる |
| 同じものに `flush=True` | 3 秒差で到着 = flush で直る層は確かにある |
| flush 済み stdout を `tail -40` へ、同内容を stderr へ | stderr は t=0 / t=4 に即着、stdout はプロセス終了後にまとめて到着 |

`tail -n 40` は `-f` なしだと「最後の N 行」を出す道具で、**定義上、入力が終わるまで
1 行も出せない**。ストリーミングフィルタではない。したがって `python -u` を足しても
明示 flush を足しても、報告された症状は直らなかった。

さらに `run.py:131` の `flush=True` はバッファ全体を押し出すため、直列実行では
シナリオごとに出力が流れていた。仮説だけでは 30 分完全無音を説明できない。

3 つめの要因もある。`runner.py` は子プロセスを `capture_output=True` で起動するので、
シナリオ実行中の 2 分間は親から出せる情報が構造的にゼロだった。

### 3. 並列化が顕在化させる既存の穴

調査中に 2 つ見つかった。どちらも直列なら無害で、並列にすると害になる。

- `runner.py` は `subprocess.run` の `returncode` を見ていなかった。子がレートリミット等で
  異常終了すると stdout が空 → 観測 0 件 → **compliance 0% というもっともらしい嘘のレポート**
  が出る。`classifier.py` が `ClassificationParseError` で既に潰していたのと同型の穴が
  実行段に残っていた
- sandbox のディレクトリ名は `scenario.id` 由来で、その id は LLM が生成する。
  分離は生成器の慣行であって保証ではない。直列なら id 重複は無害だが、並列では
  `_setup_sandbox` が作る前に消す（`shutil.rmtree`）ので、走行中の兄弟 sandbox を消す

## Decision

### 並列実行

シナリオ実行を `ThreadPoolExecutor` に載せる。`--concurrency`（既定 3 = シナリオ数、
最小 1）を新設する。スレッドで足りるのは `run_scenario` も `grade` も
`subprocess.run` のブロッキング待ちで、待機中は GIL が解放されるため。

採点はワーカーの中に置いたままにする。もともとシナリオごとのループ内にあったので、
実行を並列にすれば採点も無料で並ぶ。

生成段（spec → シナリオ）は直列のまま残す。前段の出力を次段が使う実際の依存がある。

**同時に走る `claude -p` は最大 3 プロセス**（各シナリオはある瞬間に実行中か採点中の
どちらか一方）。サブエージェントを 3 本立てるのと同じオーダー。
自動リトライとバックオフは入れない — `rules/common/debugging.md` のとおり、
レートリミットの連発は踏み抜く対象ではなく人間に上げる警報として扱う。

### 決定性の保全

完了順は**進捗表示にだけ**使う。`execute_scenarios` は `scenario.level` 昇順に
並べ直して返す。`report.generate_report` はリスト順にレンダリングするので、
これで並列でも直列でもレポートの構造が一致し、平均の加算順まで固定される。

`--spec` による spec 固定（run 間比較の機構）には触らない。

### 進捗チャネル

進捗を stdout から **stderr** に移し、あわせて明示 flush する。2 層とも直す:

- stderr 化 — `| tail -40` に吸われず端末に直接届く。今回の症状を実際に直すのはこれ
- flush — ログファイルへのリダイレクトやバックグラウンド実行でも溜め込まない

stdout に残すのは「答え」だけ（レポートの保存先、Overall Compliance、`--dry-run` の出力）。
副産物として、並列ワーカーの進捗が stdout のレポート出力に混ざる経路が消える。

`[N/4]` の直列前提は、実行段だけ**完了数**表記（`(2/3)`）に変える。
生成段の `[1/4]` `[2/4]` は本当に直列なので据え置く。

### 既存の穴を塞ぐ

- **観測 0 件**なら `ScenarioExecutionError` を上げる。終了コードは条件に含めない。
  初版は `returncode != 0 かつ観測 0 件` としていたが、これでは 3 経路が開いたままだった —
  正常終了で stdout が空、正常終了で stdout が解析不能、そして実害が大きいタイムアウト
  （`returncode` がその分岐で初期値のままなので、1 時間で殺された子が `0%` と報告される）。
  捏造されるのは「空であること」であって終了コードとは無関係だった。逆に、異常終了でも
  トレースが残っていれば採点する（`--max-turns` で打ち切られた子は実際に作業している）
- 実行前に scenario id の一意性を検査し、重複していれば `-L{level}` を付けて解消する。
  **検査は生の id ではなく正規化後のディレクトリ名で行う** — `_safe_sandbox_dir` は
  `[A-Za-z0-9\-_]` 以外を `_` に置換するので、`task/a` と `task_a` は 2 つの id で
  1 つのディレクトリになる。あわせて、正規化して空になる id は sandbox の根そのものを
  指してしまい（封じ込め判定は「ディレクトリは自分自身の内側」として通す）、
  `shutil.rmtree` に全シナリオの親を渡すことになるため、`_safe_sandbox_dir` 側でも拒否する。
  この 2 件は cross-model レビュー（codex-review）が指摘した。生の id を見て書いた検査が、
  実際に鍵になっている値を見ていなかった典型的な著者の盲点
- 生成器プロンプトの `setup_commands` 例を相対パスにする。sandbox が作業ディレクトリなので
  相対で足り、パスがディレクトリ名から独立する

失敗したシナリオは 0% として集計せず、測定失敗として stderr に出す。
残りのシナリオのレポートは保存したうえで終了コード 1 を返す。

## Alternatives Considered

**`python -u` / flush だけで済ませる** — 却下。実測 2 が示すとおり、
`| tail -40` の症状は flush では直らない。仮説のまま直していたら
「直したのに直っていない」状態になっていた。ただし flush 自体は
ログ取り・バックグラウンド実行に効くので、stderr 化と併せて入れた。

**進捗ファイル / 完了したシナリオから逐次 artifact を書く** — 却下（現時点では）。
ユーザー指示どおり「機構を足す前に flush 修正だけで足りないか先に見る」を実施した結果、
stderr 化で症状が直った。`2>&1 | tee run.log` で外部から追える。
`rules/common/planning.md` の複雑性チャレンジに従い、機構を足す前に必要性が実証されるまで待つ。

**シナリオ実行中のハートビート** — 却下。`capture_output=True` である以上、
親には出せる情報が無い。時計を刻むだけのタイマースレッドは機構の割に情報を足さない。
開始・完了・経過時間の 3 点で「止まっているか進んでいるか」は判別できる。

**asyncio への書き換え** — 却下。ブロッキング I/O 待ちなのでスレッドで十分。
`subprocess` 呼び出し 3 箇所を非同期化する変更に見合う利得が無い。

**sandbox のディレクトリ名を code 側の値（level）に変える** — 却下。
`setup_commands` が絶対パスでディレクトリ名を埋め込んでいたため、名前を変えると
skeleton 作成が壊れる。代わりに生成器プロンプト側を相対パスにして結合を切り、
名前は id 由来のまま一意性だけ保証した。信頼境界のコード（`_contained` /
`_apply_setup_commands`）を触らずに済むのが決め手。

**レートリミットで自動リトライ** — 却下。`rules/common/debugging.md` と
`skills/learned/platform-governance-aggregate-pattern.md`（2026-08-23 の skill-stocktake で
退役。内容は `skills/authorship-strategy/SKILL.md` に吸収済み — aggregate-pattern test と
2026-07-16 の全損事例を L255,272 が保持）のとおり、連発は substrate からの policy シグナル。
停止して報告する。

## Consequences

**得るもの**

- 実行 + 採点段の壁時計が 3 本の合計から「最も遅い 1 本」に縮む。
  生成段は直列のまま残るので、全体の短縮率は実測して記録する
- 長時間 run の途中経過が、パイプ越し・バックグラウンドでも見える
- 壊れた測定が 0% レポートに化けなくなる（並列化と独立した改善）
- sandbox の分離が慣行から保証に変わる

**払うもの**

- `run.py` に並行実行の複雑さが入る。決定性はテストで固定した
  （完了順を逆転させても level 順に返ること、進捗が stdout に出ないこと、
  失敗が 0% にならないこと、`--concurrency 1` が直列であること）
- 同時 API 呼び出しが 1 → 3 になる。レートリミットに当たった場合は
  `--concurrency 1` が逃げ道になる
- 測定失敗時の終了コードが 0 → 1 になる。部分的な測定を「完了」と読む
  自動化があれば影響を受けるが、この skill は対話起動が主なので影響は小さい

**レビューで判明した追記（2026-08-01、同日中に修正）**

コミット後に python-reviewer / security-reviewer を回したところ、この ADR の記述と
実装の双方に誤りが見つかった。いずれも再現を取ってから直している。

- **決定性の主張が偽だった** — `sorted` は安定ソートなので、`level` だけで並べると
  同順位は挿入順（＝完了順）を保つ。`level` は LLM の YAML から素通しで一意性の保証が無く、
  level 2 が 2 本ある入力で直列 `[alpha, beta, competing]` / 並列 `[beta, alpha, competing]` と
  実際に食い違った。並べ替えの鍵を `(level, 提出順)` に変更
- **sandbox 一意性が呼び出し側任せだった** — `ensure_unique_sandbox_ids` は `main()` からしか
  呼ばれず、`execute_scenarios` は渡された id をそのまま N 並列に展開していた。
  破壊的な帰結を持つ保証は、危険を作る関数の側に置く。`execute_scenarios` の冒頭で呼ぶ
- **大文字小文字だけ違う id を別物と見ていた** — macOS の APFS は case-insensitive なので
  `fix-bug` / `Fix-Bug` は 2 つの `Path` と 1 つの inode（実測）。衝突判定を case-fold した名前に変更
- **封じ込めに `..` の抜け道があった（既存欠陥）** — `_contained` は実在する最も近い祖先だけを
  resolve して残りを繋ぎ直すため、存在しない要素の後ろに置かれた `..` は解決されずに残り、
  `Path.parents`（正規化しない）がそれをただのディレクトリ名として扱って base を鎖に残していた。
  `a/../../elsewhere/x` が sandbox 外に実際に作られることを確認。`normpath` を probe の前に挟んで修正。
  本 ADR の変更が生成パスを 100% 相対（＝この分岐）に寄せたため、露出は増していた
- **自作 skill の pytest がゲートから走っていなかった** — 回帰テストを書いても検査層が
  実行しないなら守られない。`.claude/verify.sh` の full mode に配線した（→ `.claude/verify.md`）

修正後に同じ security-reviewer へ修正の検証（反証を試みさせる形）を依頼し、
4 項目とも保持を確認。その過程でさらに 3 件出て、いずれも同じ作業内で直した。

- **`--dry-run` が検査すべきものを見せていなかった** — SKILL.md は「信頼できない .md を
  測るときは `--dry-run` で生成されたシナリオを先に読むこと」と案内していたが、実際に出るのは
  spec の step と説明文 60 文字だけで、**攻撃者が制御する 2 フィールド**（無人の子に渡される
  `prompt`、ファイルシステムを触る `setup_commands`）を一度も出していなかった。
  文書化された緩和策が、主張している中身を見せていない状態。両方を全文出すよう変更
- **壊れた symlink が封じ込めを抜けた** — `Path.exists()` は link を辿るので dangling link は
  「不在」と読まれ、未解決の tail に落ちて `touch` が link 先にファイルを作る。
  untrusted な経路からは到達不能（sandbox は空で作り直され、2 語彙は symlink を作れない）だが、
  symlink テストが閉じていると示唆している境界そのものなので `os.path.lexists` で閉じた
- **制御文字の除去が 3 経路で漏れていた** — シナリオ一覧の `description`、`_report_failures` と
  `_completion_line` の例外メッセージ（`classifier.py` だけが `!r` を使わず子の stderr を
  素通ししていた）。フィルタを幅指定から分離して全経路に適用

**残る制約**

- `2>&1 | tail -40` は依然として何も出さない。`tail` の性質でコードでは直せないため、
  SKILL.md に注意書きで対処した
- scenario prompt は毎回 LLM 生成で変動する。run 間比較の固定は spec までという
  既存のスコープは変わらない

**実測（2026-08-17）**

上の「全体の短縮率は実測して記録する」の宿題。`skills/implementation-chain/SKILL.md` を対象に
`--spec` なしの full run 1 本（gen=haiku / exec=sonnet / classifier=sonnet、`--concurrency 3` は既定、
12 step spec を新規生成、Overall Compliance 67%、exit 0）。

| 段 | 所要 | 並列性 |
|---|---|---|
| spec 生成 | 1m55s (115s) | 直列 |
| シナリオ生成 | 0m37s (37s) | 直列 |
| 実行 + 採点 | 7m41s (461s) | 3 並列 |
| **全体** | **10m13s (613s)** | |

| シナリオ | 実行 + 採点 |
|---|---|
| supportive | 7m41s (461s) |
| neutral | 1m50s (110s) |
| competing | 0m31s (31s) |
| 合計（直列ならこれだけ待つ） | 10m02s (602s) |

**「最も遅い 1 本に縮む」は厳密に成立した** — 実行段の 461s は最遅シナリオの 461s と一致し、
合計 602s ではない。**一方、「概ね 1/3」は成立しない。** 実行段は 602s → 461s（76.6%、1.31x）、
全体は直列相当 754s（生成 152s + 合計 602s）→ 実測 613s（81.3%、1.23x）で、短縮は 141s。

差の原因は所要のばらつきで、遅さそのものではない。`max = 合計/3` になるのは 3 本が等速のときだけで、
実測は最速 31s と最遅 461s の**約 15 倍差**だった（supportive は chain 全体を回し、competing は
早い段階で TDD を省いて終わる）。並列化の利得は最遅シナリオが支配し、上限は `max/合計` になる。
`--concurrency 1` に落としたときの実測差は 141s と読める。

この run は 2026-08-17 の sandbox 実行単位分離（`SANDBOX_BASE/run-<pid>/<id>`）も同時に通しており、
3 シナリオは `run-<pid>` 配下に分かれて作られた。上の「sandbox の分離が慣行から保証に変わる」は
プロセス内の保証で、プロセス間はこの日まで開いていた。
